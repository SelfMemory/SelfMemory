SelfMemory Architecture Blueprint

The open-source Python backend for the LLM Wiki: one domain core, exposed equally through a REST API, a CLI, an MCP server and an A2A agent. The Next.js UI lives in its own repository and talks to the backend only through the published API contract.

Request lifecycle

Where it starts and how it flows

Every entry point is a thin adapter. It authenticates, converts input into a typed command, and calls the same application service. No adapter holds business logic, so a feature written once is available everywhere.

Today the boot point is server/main.py (FastAPI on :8081) plus the separate selfmemory-mcp/main_unified.py. The target is one composition root, selfmemory/bootstrap.py, that wires adapters to services, so the API, CLI, MCP and A2A processes all start from the same container.

Multi-layer architecture

InterfacesFastAPI routers, MCP tools, A2A skills, CLI commands. Parse, authenticate, call a service, format the reply.
ApplicationUse cases such as IngestUpload, StartRun, AskWiki. Transactions, authorization checks via access, event emission.
DomainScope, Page, Run, Org/Project. Pure Python, no I/O, no framework imports. Path safety and scope rules live here.
PortsProtocols: WikiRepo, JobQueue, Sandbox, IdentityProvider, SearchIndex.
InfrastructureAdapters: Mongo, git, bwrap/docker, opencode, Ory, FTS. Swappable without touching the layers above.

import-linter contracts in CI: domain imports nothing above it; interfaces never import infrastructure directly.

How new work lands

Adding a feature tomorrow

A new capability is a new folder under features/ with the same five files. Each feature exposes a register(app_ctx) function; apps/api.py discovers features through a registry (an explicit list, or Python entry points for plugins), so routers, MCP tools, A2A skills and CLI commands appear without editing a central file.

features/
  timeline/
    __init__.py      # FEATURE = Feature(name="timeline", register=register)
    domain.py
    ports.py
    service.py
    adapters/
    interfaces/{http,mcp,a2a,cli}.py

Third parties can ship features as separate packages using the selfmemory.features entry-point group.

One service, four front doors

CLI, MCP and A2A native

REST / OpenAPI

  • Versioned under /api/v1
  • SSE for run progress
  • OpenAPI spec is the UI contract

CLI

  • selfmemory wiki ingest ./docs
  • Local mode calls services in-process
  • Remote mode calls the API with an API key
  • --json output for scripting

MCP

  • Mounted at /mcp on the main app (Streamable HTTP)
  • Tools, resources (wiki pages as wiki:// URIs) and prompts
  • OAuth 2.1 via Hydra, with per-scope tokens
  • stdio mode via the CLI for local clients

A2A

  • Agent Card at /.well-known/agent-card.json
  • Skills: ingest, ask, summarise, run status
  • Long runs map to A2A tasks with streaming updates
  • Same auth as MCP

A small decorator (@capability) on a service method can generate the MCP tool and A2A skill schema from its Pydantic signature, so the four surfaces stay in sync.

Runners, sandboxes and sessions

Agent runtime and isolation

Recommendation: one short-lived sandbox per turn, not per user and not per session. The conversation continues because the opencode session state is saved between turns, not because a process stays alive. bwrap starts in about 10 ms, so a fresh sandbox per question costs almost nothing. It also means permissions are checked again on every turn, and a crash or leak can't outlive a single answer.

What a sandbox can see

User selectsMounted read-onlyMounted writableNever mounted
One projectThat project's wiki, its sub-projects the user can read, the org roomNothing (questions are read-only)Other projects, other users' personal scopes, other orgs
All my projectsEvery scope in OrgAccess.scopes for this user, which is the union of what they can readNothingProjects they aren't a member of, other users' personal scopes

The sandbox only ever contains directories the user is allowed to read. Anything else is never bound in, so it doesn't exist inside the run. This is how selfmemory/wiki/sandbox.py works today, and it should stay the only mechanism.

Session home rules (the leak to watch)

  • opencode transcripts contain the text of every file a run has read. The session home must therefore be keyed by (org, user, chat, scope-set hash).
  • If the user changes the selected scopes, or loses access to a scope, start a new opencode session. Never let an old transcript carry content from a scope the user can no longer read.
  • Session homes are never shared between users, even inside the same org. An org-level shared chat runs under the requesting user's permissions.
  • Delete the home when the chat is deleted, and expire it on a retention timer (for example 30 days).

Coding agents as callers (A2A and MCP)

A coding agent such as Claude Code or Cursor asking on a user's behalf already keeps its own conversation. It doesn't need us to remember much. Design for three things: it may send several questions at once, it may wait or poll, and it may disappear without saying goodbye.

SituationBehaviour
Question with no contextIdStateless one-shot task. New sandbox, new opencode session, nothing carried over. This is the default for coding agents.
Follow-up with a contextIdContinues that context's opencode session in a new sandbox
Several questions at once, different or no contextsRun in parallel, one sandbox each, up to the user's limit (for example 4). Anything over the limit waits in the queue with state submitted
Several questions at once on the same contextIdRun one after another in arrival order, because one opencode session can't take two turns at once. The second task stays submitted until the first finishes
Caller wants to waitmessage/stream (SSE), or blocking message/send with a timeout
Caller wants to fire and check backNon-blocking send returns the task at once; the caller uses tasks/get, tasks/resubscribe, or a push-notification webhook
Caller drops the connectionThe run keeps going to completion. The result is kept so the caller can resubscribe. tasks/cancel kills the sandbox
Permissions change mid-contextThe next task starts a fresh session (the scope-set hash changed)
WhatKeep forWhy
Task result and status24 hLong enough to resubscribe or poll after a disconnect
A2A context (opencode session)1 h idle, then deletedA coding agent's follow-ups come within minutes; it holds its own long-term history
App chat transcriptsUntil the user deletes the chat, or the org retention limitPeople come back to these
Audit record (who asked what, which scopes were mounted)Org policy, no file contentCompliance without keeping data copies

Make every one of these a per-org setting with these defaults. If a coding agent needs to check facts in detail, steer it to the MCP file tools: they need no sandbox or model on our side and run in milliseconds.

MCP tools and permissions

The MCP client's own model does the reasoning, so the server only needs to provide safe file access. Every tool resolves paths through OrgAccess.resolve_path. Allowed access is the user's role intersected with the OAuth scopes on the token (wiki:read, wiki:write).

ToolNeedsNotes
list_scopesreadOnly scopes this user can read
list_files, read_file, searchreadSub-projects the user can't read are hidden
write_file, delete_filewrite on that scopeEach write is a git commit with the user as author
ingestwrite on that scopeQueues a sandboxed run and returns a run id
ask_wikireadOptional. Server-side agent answer for clients that want one
run_statusreadProgress of a queued run

Why not a long-lived sandbox per user or per session

Per turn (choose this)

  • Permissions re-checked every turn
  • Workers stay stateless, so any worker can take any job
  • Idle users cost nothing
  • Cost: opencode startup per turn, about 1 to 2 s

Per session, kept warm

  • Faster follow-up answers
  • Has to be pinned to one worker and evicted after idle time
  • Has to be killed when permissions change
  • Add later only if startup latency hurts, using opencode serve with a 5 to 10 minute idle limit

Per user

  • Mixes scope sets across chats
  • One mistake leaks between that user's chats
  • Lots of idle processes
  • Not recommended

Scaling the runners

  • Run workers as their own pool (SELFMEMORY_WORKER=off on the API). Mongo leases already let any number of workers share the queue.
  • Session homes go on shared storage (or are synced to object storage between turns), so the next turn can run on any worker.
  • Schedule fairly per org, with concurrency limits per user and per org, so one tenant can't take all the runners.
  • Keep a pool of pre-started, empty sandboxes; mounts are added when a job claims one.
  • When moving from bwrap to multi-tenant hosts, use gVisor or Firecracker microVMs per run. The mount-set model stays the same.
  • Each run has a hard timeout, CPU and memory limits, and network access only to the model provider.

LLM Wiki delivery sequence

Phased development

Phase 0

Stabilise

Merge feat/orgbrain-backend. Pin Python 3.13, add pydantic-settings, add import-linter with the current layers.

Phase 1

Restructure

Move to features/ layout behind the composition root. Delete the embeddings, vector store, LLM and old memory modules, along with their routes, tests and dependencies. Version the API at /api/v1.

Phase 2

Wiki core

Ingest, scopes, git history, search index, graph and timeline, runs with SSE progress. OpenAPI contract published and TS client generated.

Phase 3

New UI

Next.js app consumes the generated client. Wiki browse, upload, run, chat. Old memory screens retired at parity.

Phase 4

Agent native

MCP mounted in the main app with OAuth 2.1, Typer CLI with local and remote modes, A2A Agent Card and task skills.

Phase 5

Scale and harden

Separate worker pool, Keto permissions, stronger sandbox, queue swap, per-org quotas and audit log.

Phase 6

Ecosystem

Feature plugins via entry points, public SDKs, self-host Helm chart.

Needs a call

Decisions

Decided: remove the legacy memory and vector stack entirely. Use a single repo with packages/, with selfmemory-mcp folded into the core package as one feature interface. Retention defaults are set (see Agent runtime).

Still open:

  • Keto vs keeping authz in server/wiki/access.py.
  • When to move the job queue off Mongo.
  • Whether follow-up latency justifies warm per-session sandboxes.
  • Default concurrency limit per user and per org.
