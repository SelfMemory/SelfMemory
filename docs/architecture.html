Pages, Not Vectors

Memory stored as markdown pages that an agent rewrites, instead of embedded chunks that accumulate. One folder per project, one git repo behind it, and an agent that reads it with grep the way a person would.

The shift

Why the store changes shape

Vector memory answers what looks like this query. That is the wrong question for personal memory, where the thing you want is what do we currently know about X. The difference shows up on the third write: a correction does not replace the claim it corrects, it lands beside it, and retrieval now returns both with no way to tell which is live.

Compaction fixes this at write time instead of query time. A new source is merged into the pages it affects, so the store holds one current answer per subject and the contradiction is resolved once, by a model that saw both claims, rather than on every read forever.

Storage

A project is a folder is a repo

Organizations contain projects contain users — the RBAC already in server/. Each project gets a directory of markdown pages, and each directory is a git repo held in durable storage. Sessions clone it; nothing long-lived runs on a mounted disk.

Git is doing real work here, not just persistence. It gives per-page history and blame, rollback when a compaction goes wrong, what did my memory learn this week as a log, and — the part that matters most — a push rejection where a plain filesystem would silently lose a write.

org_acme/ ├── proj_selfmemory/ linked — joins org-wide queries │ ├── index.md page catalogue, one line each │ ├── log.md append-only operation record │ ├── schema.md conventions the agent follows │ ├── inbox.md un-compacted writes land here first │ └── pages/ │ ├── project/selfmemory.md │ ├── topic/tooling.md │ └── person/shrijayan.md ├── proj_website/ linked └── proj_payroll/ isolated — never joins a multi-project session

The linked / isolated flag is set when the project is created and decides one thing: whether this repo may be cloned into a session alongside others. Isolated is absolute — it holds for org owners too. An exception for admins would make the guarantee meaningless, and an admin who needs the data can still query that project on its own.

Write path

Ingest returns before the thinking starts

Compaction costs an agent session. Paying that inline would make remember() a multi-second call, so the request only appends to inbox.md and returns. A per-project worker drains the inbox in batches — on a timer, or at N entries.

That queue is also the concurrency fix. One worker per project means two ingests can never rewrite the same page at once, which is the failure mode that would otherwise corrupt memory silently and stay invisible for months.

Read path

Permissions decide the mount, not the answer

A query resolves RBAC first, then clones only the repos that user may read and that are not marked isolated. The session sees exactly that set — filtering after the agent has read something is not filtering, and mounting broadly to sort it out later is the leak.

Sessions that span more than one project get read-only tools. Mount two projects with write access and a page in one, written from a user-supplied source, can instruct the agent to copy the other project into it. One invariant closes that: writes only ever happen in a single-project session.

Invariants

Four rules the implementation cannot bend

writes

One worker per project, always

Concurrent compaction of the same repo is a lost update with no error and no trace. Serialize at the queue; ingest is already asynchronous, so nothing gets slower.

scope

Multi-project sessions are read-only

Write tools exist only in a session holding exactly one repo. This is what stops injected page content in one project from exfiltrating another into itself.

scope

Permissions gate the clone, not the response

Resolve what the caller may read before anything is written to session disk. Anything mounted is assumed read, whatever the answer ends up saying.

truth

Page bodies live in exactly one place

The repo is the source of truth. Postgres holds identity, RBAC, the queue, billing and a light index for listing pages — never a second copy of a body to reconcile.

Encryption

Encrypted at rest, plaintext where it must be

Encryption is global and always on — there is no per-project toggle. A toggle would make the security posture unstateable in a questionnaire, offer users a choice where one answer is always the right-looking one, and fork the retrieval path forever.

Keys stay derived per project by HKDF from a master key — the scheme already in selfmemory/security/encryption.py, which fits one-key-per-repo better than it fitted the vector payload. Per-project keys, global policy: the key scope and the customer-facing choice are independent, and conflating them is what makes a toggle look reasonable. The unit changes — the page body as one blob, not four named fields.

WhereStateWhy
Project repo, at rest encrypted Fernet over the page body, key derived per project_id
In transit encrypted Ordinary transport security
Session working copy plaintext The agent has to grep it. Keep it on tmpfs, wipe on teardown, never touch host disk
Model provider plaintext Unavoidable when a model maintains the pages. Mitigated by a zero-retention agreement, not by keys
The cost is cold start, not search. Encryption looks like it kills the fast answer tier, because ciphertext cannot be indexed server-side. It doesn't: the fast tier needs a decrypted working copy, and the session already has one on tmpfs. Ripgrep plus one model call over the hits is the fast tier, running inside the session over data that is encrypted at rest. What actually costs time is booting a cold session — which makes this a caching problem (keep a warm clone for recently active projects) rather than a reason to fork the data model.
The enterprise axis is whose key, not whether. Platform-managed by default; customer-managed KMS per organization for enterprise. That is the upsell enterprises actually ask for, and a per-project toggle would sit directly in its way.

Unresolved

Two decisions still open

01

What drains the inbox — time or volume? A timer gives predictable cost; a threshold gives fresher memory. It sets how stale a just-written fact may be when read.

02

How much does the agent runtime get to be load-bearing? Behind an adapter it stays swappable; wired straight through, it is faster to build and harder to leave.
